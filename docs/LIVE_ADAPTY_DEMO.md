# Lumen with live Adapty reads

This demo connects Reconcile to the isolated **Lumen - AI Photo Editor
(Hackathon)** app, created by the official Adapty hackathon seed. Adapty API
responses, local Lumen gate decisions, SDK delivery, incident detection,
automatic policy decisions and client repair actually execute. The purchase
records are synthetic. They do not prove that a card or app-store account was
charged.

## One-time setup: the private configuration

The connected demo needs a private configuration file at
`reconcile-mock-first-kit/runtime/live-adapty/live-config.json`. That directory
is git-ignored, so the file is **not in the repository**; a fresh clone can run
only the mock mode (`npm start -- --mock`) until the file exists.

The file is generated by `reconcile-mock-first-kit/adapty_seed_setup.py`. The
script needs:

- An installed, authenticated Adapty CLI (`adapty`) that can read the isolated
  app. The live adapter is pinned to app ID
  `46a573aa-8c90-4b4b-ba72-2349ae9fb030` and the exact title
  `Lumen - AI Photo Editor (Hackathon)`; a configuration for any other app is
  rejected at startup.
- A local checkout of the official seed repository,
  [adapty-seed-data-hack at 77d39ed](https://github.com/kpotehin/adapty-seed-data-hack/tree/77d39ed807a66bbebcf24fe67c42be4fc9ef4c82).
  The script verifies pinned checksums of `seed_adapty.py` and
  `data/lumen_dataset.json.gz` before doing anything.
- The app with its products, flows, placements and experiments already created
  through the Adapty CLI. The script runs the official seed with
  `--skip-config`, and this repository does not script the app creation itself.

```sh
python3 reconcile-mock-first-kit/adapty_seed_setup.py \
  --source <path-to-adapty-seed-data-hack-checkout> \
  --app-id 46a573aa-8c90-4b4b-ba72-2349ae9fb030
```

This is a write to Adapty: the official script sends profiles and synthetic
transactions through Adapty's server API, keeping its original attribution wait
and request budget. The setup script then writes these private files (mode
0600, in a 0700 directory) under `reconcile-mock-first-kit/runtime/live-adapty/`:

| File | Content |
| --- | --- |
| `adapty-secret.key` | The app's secret key, captured from the CLI without printing it |
| `seed-started.json`, `seed-status.json` | Seed revision, checksums, start/finish time, counts and customer prefix |
| `official-seed.log` | Output of the official script, with the key redacted |
| `live-config.json` | Written only after a fully successful seed: `app_id`, `title`, `secret_key_file` (absolute path), `environment` (`hackathon_seed`), `source_environment` (`Production`), the `seed` status and exactly 100 unique `customer_user_ids` |

The script refuses to start twice in the same runtime directory. Do not rerun
the seed to reset an incident. A partial seed requires inspection of its
private status and log, not a blind replay. Because `secret_key_file` is an
absolute path, the configuration is not portable to another machine without
editing that path.

The setup used for the results in this document:

- Completed on 2026-11-07: **6,000 profiles, 3,123 synthetic transactions,
  1,000 flow views; zero failures**. Customer prefix: `lumen_916965_`.
- The pre-existing `Test` app in the same Adapty account was left untouched.
- No key belongs in Git, screenshots, exported reports or frontend code.

The official script labels store transactions `Production`. That value is
retained as source metadata; it does not turn synthetic seed transactions into
real payments. Our local environment is `hackathon_seed`.

## Run the connected demo

From the repository root:

```sh
npm run start:live -- \
  --runtime /tmp/reconcile-live-demo \
  --port 0 --live-bootstrap-pending
```

`--runtime` is any new, empty local directory; `--port 0` picks a free port.
Without arguments, `npm run start:live` reads the configuration from the
default path above, uses the runtime directory
`reconcile-mock-first-kit/runtime/live-adapty/demo` and listens on port 8876.
`--live-bootstrap-pending` must be used only with a new runtime directory.

`npm start` (without `--mock`) starts the same connected demo on port 8875
whenever the private configuration exists, and adds `--live-bootstrap-pending`
automatically when the default runtime directory does not exist yet.

The launcher prints the Reconcile and Lumen URLs. It starts three isolated local
processes; the source adapter performs read-only Adapty requests. It never grants
access or changes a purchase at Adapty. The selected registry contains 100 exact
customer IDs from the official seed; the adapter verifies their current source
state independently.

The CLI also reads all six catalog products at startup. Public status and audit
include its version, observation time and a catalog checksum. Account reads use
the server API; CLI commands are not run for every gate request. Keep the
existing CLI session authenticated and the private key file available.

1. Open the printed Reconcile URL and confirm the source registry contains 100
   accounts. The **Run** button stays disabled until the source is ready.
2. Choose **Run**. The new Lumen runtime awaits initial application; normal
   handler replay succeeds for 76 accounts and exercises 24 local failures.
   These are existing synthetic Adapty records, not new payments.
3. Reconcile detects unapplied access proactively, without a customer gate request
   or manually opened incident. Source observation alone never changes access.
4. Watch the incident move from detection to repair to the verified result:
   23 restored gates and one unresolved application failure remain visible.
   Each repair rechecks the current Adapty entitlement, resyncs Lumen and
   probes the same authorization decision used by the customer endpoint.
5. Choose **Run** again for continuous later failures on healthy accounts. While
   the simulation is running the same button reads **Stop**; it prevents the
   next fault while monitoring and current recovery continue.
6. Download activity for a chosen UTC `[from,to)` period as CSV or JSON. Detailed
   observed steps and their owners are available in each incident's Activity.

The connected monitor has a single **Run** / **Stop** button. The **Run once**
and **Start/Stop demo traffic** controls described in the main README belong to
the mock mode only.

The policy `local-fulfillment-resync-v2` records the exact authorization without
requiring an operator click. It allows only existing local access to be resynced
and verified. Unclear evidence remains unresolved. See
[automatic recovery and measured overhead](AUTOMATIC_RECOVERY.md).

The explicit `/recovery-console.html` URL retains the detailed console, the
fixed 24-account injection, the Lumen gate and HTML audit export. To replay the
earlier manual workflow, start a fresh runtime with `--manual` (and without
`--live-bootstrap-pending`) and use `/recovery-console.html`.

The live plan contains client resync and gate verification only. The existing
mock payment-activation scenarios still exercise provider validation and catalog
repair separately. A missing, changed, expired or ambiguous live source blocks
repair; a source entitlement is never reported as independently verified money.

## Expected results

The reference replay on 2026-11-08 used fresh isolated Lumen storage and real
read-only Adapty evidence: **100 observed rights → 76 normal handler successes /
24 failures → one 24-account incident → 23 restored gates / one unresolved**.

- Detection preceded any customer denial or manual incident. Actual customer
  gate requests then returned 23 HTTP 200 and one HTTP 403 without creating
  another incident.
- The trace includes 24 original handler receipts and 23 repair receipts.
- The SDK delivered 346 events including those gate requests, with zero drops,
  errors or remaining backlog.
- The replay interval observed 299 physical source requests, including
  background polling.

A separate replay verified restart history and two later recoveries on healthy
accounts outside the original 24. Browser checks passed at 1280px and 390px,
including keyboard operation of the Run/Stop control, preserved focus during
polling, trace details and CSV/JSON downloads. Both exports contain all three
incidents while the filtered UI shows one row, with UTC
`[2026-11-08,2026-11-09)` and summaries 24/23/1, 1/1/0 and 1/1/0.

The result files and screenshots from these runs were kept locally and are not
committed. The seeded subscriptions have real expiry timestamps, so readiness
and the exact counts can change over time. Source reads and repair preflight
must remain fresh.

## Acceptance harnesses

Both harnesses use public HTTP only and do not reseed or modify the remote app.
`--output` is optional; `.artifacts/` is git-ignored, so the result file stays
on your machine.

The automatic harness needs a fresh runtime started **without**
`--live-bootstrap-pending`. It injects the fixed 24-account incident, waits for
recovery without sending an operator approval, then runs three randomized
incidents and checks stable history, source snapshots and actual gates:

```sh
npm run test:auto -- --url http://127.0.0.1:8876 \
  --output .artifacts/automatic-recovery-acceptance.json
```

The manual harness needs a fresh runtime started with `--manual`. It checks the
100-account scope, automatic 24-account detection, blocked unapproved writes,
the exact 48-step plan, duplicate execution, the immutable approved snapshot,
24 actual successful customer gates, and the absence of credentials and
fabricated payment proof in the audit:

```sh
npm run test:live -- --url http://127.0.0.1:8876 \
  --output .artifacts/live-adapty-acceptance.json
```

- **Automatic downstream recovery:** 100 registered accounts → 24 affected →

  plus three further random incidents (7, 5 and 4 accounts); 1,248 SDK events,
  zero drops or errors.

Both passed browser checks on desktop and at 390px, and both ended with zero
unresolved accounts; the current replay keeps one unresolved application
failure visible.

## Operating notes

Historical telemetry before startup and the future portion of an incident window
remain incomplete coverage. That does not prevent individually supported repairs,
and the report keeps those gaps visible after recovery.

The automatic simulator supports repeated runs in the same runtime and retains
each incident's result. To start with an empty history, stop the launcher and
choose a **new local runtime directory**. This does not rerun the official seed.

## What the SDK monitors

The server SDK records allowlisted application observations: source entitlement
reads, handler/projection changes and actual gate decisions, with account,
configuration version, timestamps and correlation IDs. Its signed durable outbox
delivers these asynchronously; collector failure must not block the customer.
The engine combines those observations with its own source reads to decide
whether an account is affected. SDK messages alone do not verify payments.

This integration uses Adapty's [Get profile API](https://adapty.io/docs/api-adapty/operations/getProfile)
as an entitlement source. Renewal cancellation and access expiry are separate
facts; [Adapty's webhook contract](https://adapty.io/docs/webhook-event-types-and-fields)
describes that distinction. No webhook was received from a real store in this demo.

Limits: no real store checkout, native mobile SDK, production deployment or
payment-provider attestation. The premium gate proves authorization, not a full
photo-editing service. Commercial value still requires the
[Adapty pilot](PILOT_BRIEF.md).
